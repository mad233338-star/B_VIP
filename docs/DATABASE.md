# B_VIP Tool — Database Guide

**Engine:** PostgreSQL 14+ (16 recommended) · **Access:** EF Core 8 / Npgsql · **Schema owner:**
the application role (`b_vip_app`), never `postgres`.

---

## 1. Conventions

- Primary keys are `uuid`, generated by the application (`Guid.NewGuid()`), so offline clients can
  create ids that stay unique.
- Table and column names are `snake_case`; a few legacy columns keep their entity name
  (`"CreatedUtc"`) and are therefore quoted in SQL — always quote identifiers in ad-hoc queries.
- All timestamps are `timestamptz` in UTC. Required timestamps default to `now()`; nullable
  timestamps (`RevokedUtc`, `CompletedUtc`, `LockedUntilUtc`, …) stay `NULL` until the event
  happens.
- Deleting an account is a soft delete (`users."IsDeleted"`); audit, license and operation records
  are never deleted by the application.
- JSON payloads (`settings`, `diagnostic_reports.content_json`, …) are stored as `jsonb` on
  PostgreSQL.

### Key relationships

```
users 1─n user_roles n─1 roles n─n permissions (role_permissions)
users 1─n licenses 1─n license_activations
users 1─n device_service_operations 1─n operation_events
users 1─n diagnostic_reports 1─n report_attachments
users 1─n service_tickets 1─n ticket_messages
licenses 1─n license_verification_events
```

`device_service_operations.license_id` records which license allowed the run, so a support
question ("who allowed this flash?") is answerable years later.

## 3. Migrations

The schema is produced by EF Core migrations in `src/B_VIP.Infrastructure/Data/Migrations`.

```powershell
# apply pending migrations (the backend also does this on start)
dotnet ef database update --project src/B_VIP.Infrastructure --startup-project src/B_VIP.Backend

# add a migration after a model change
dotnet ef migrations add <Name> --project src/B_VIP.Infrastructure --startup-project src/B_VIP.Backend --output-dir Data/Migrations

# script it for a DBA review
dotnet ef migrations script --idempotent --project src/B_VIP.Infrastructure --startup-project src/B_VIP.Backend -o migrate.sql
```

Migration history is stored in `__migrations_history` (not the EF default, so it cannot collide with
another application sharing the database).

On start the backend logs one of:

- `Database schema is up to date`
- `Applying N pending migrations`

If a migration fails the process stops with a fatal log entry and the service does not serve
traffic.

## 4. Seeded reference data

`IDataSeeder` runs after migrations and is idempotent. It creates:

| Data | Rows |
|---|---|
| Roles | User, Support Staff, Supervisor, Finance Manager, General Manager, Super Admin |
| Permissions | 25 keys (`users.read` … `admin.releases`) |
| Role grants | Default matrix from `Permissions.DefaultForRole` |
| License plans | trial, monthly, quarterly, annual, lifetime, custom |
| Support categories | Activation & Licensing, Device not detected, Tool / driver problem, Account recovery, Billing, Other |
| Settings | branding, support contacts, default language, retention |
| Integrations | Placeholder payment, e-mail and SMS integrations (disabled) |

Re-running the seeder never duplicates rows and never overwrites values an administrator changed.

## 5. Routine SQL

```sql
-- active sessions for one user
SELECT s.id, s."CreatedUtc", s."LastSeenUtc", s.ip_address
FROM user_sessions s JOIN users u ON u.id = s.user_id
WHERE u.normalized_user_name = upper('TECH.ONE') AND s."RevokedUtc" IS NULL;

-- operations that need a human
SELECT id, operation_type, status, "QueuedUtc", summary
FROM device_service_operations WHERE status = 7 /* RequiresAttention */ ORDER BY "QueuedUtc" DESC;

-- licenses expiring in the next 14 days
SELECT l.license_key, p.name, l."ExpiresUtc", u.user_name
FROM licenses l JOIN license_plans p ON p.id = l.plan_id JOIN users u ON u.id = l.user_id
WHERE l.status = 1 AND l."ExpiresUtc" BETWEEN now() AND now() + interval '14 days';

-- audit trail for one entity
SELECT "OccurredUtc", actor_user_name, action, outcome, message
FROM audit_events WHERE entity_id = '<uuid>' ORDER BY "OccurredUtc" DESC;

-- table sizes (find the heavy tables)
SELECT relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r' ORDER BY pg_total_relation_size(c.oid) DESC LIMIT 15;
```

## 6. Backup and restore

```powershell
# logical backup (custom format, compressed)
pg_dump --host 127.0.0.1 --port 5432 --username b_vip_app --dbname b_vip `
        --format custom --compress 9 --no-owner --file b_vip-YYYYMMDD.dump

# restore into an empty database
pg_restore --host 127.0.0.1 --port 5432 --username b_vip_app --dbname b_vip `
           --no-owner --clean --if-exists b_vip-YYYYMMDD.dump
```

`deploy/backup-database.ps1` wraps the first command, adds retention and can be scheduled. The
admin API records backups under `backup_records` so the UI can show their history.

Guidelines:

- Enable PostgreSQL WAL archiving if the shop cannot afford to lose a day of tickets.
- Restore into a **separate** database first when rehearsing; never overwrite production to test.
- After a restore, all sessions and refresh tokens remain valid until they expire — revoke them
  from the admin screen if the restore crossed a security incident.

## 7. Retention

| Data | Setting | Default |
|---|---|---|
| Audit events | `Storage:AuditRetentionDays` | 730 days |
| Diagnostic reports | `Storage:ReportRetentionDays` | 180 days |
| Login attempts | not pruned automatically | keep for investigations |
| Sessions / refresh tokens | pruned when expired | — |

Implement pruning with a scheduled SQL job if the tables grow beyond your backup window, for
example:

```sql
DELETE FROM audit_events WHERE "OccurredUtc" < now() - interval '730 days';
DELETE FROM diagnostic_reports WHERE "CreatedUtc" < now() - interval '180 days';
```

## 8. Troubleshooting the database

| Symptom | Cause / fix |
|---|---|
| `28P01 password authentication failed` | Wrong password in `ConnectionStrings:Default`; check the service environment variable |
| `3D000 database "b_vip" does not exist` | Run `deploy/create-database.sql` |
| `42P01 relation "users" does not exist` | Migrations did not run; start the backend and read the log |
| `55000 cannot connect to invalid database` | The cluster lost a database directory (unclean shutdown). Drop and recreate that test database |
| Migrations extremely slow on Windows | Development cluster with `fsync` on; disable it for throw-away test clusters only |
| Deadlocks during heavy imports | Run bulk imports in one transaction per batch; do not edit license rows while clients verify |
